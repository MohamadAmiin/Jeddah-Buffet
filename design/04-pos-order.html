Sample 04 · routes/(pos)/order

The order screen

A dine-in check at table 4, mid-service, on a device that has been offline for a few minutes. Four blocks: how the order is being taken, which part of the menu is showing, the menu itself, and the guest check — which is permanent and never unmounts, because the cashier must never navigate away to see what has been rung in.

The POS is light, and pinned that way in both themes. It used to stay dark in both themes; tokens.css §3 reversed that. Press Toggle theme — the device moves with the page. What data-surface="pos" still changes is the ground/key relationship and the density: a deeper ground than the dashboard, so the white key faces read as the raised, pressable thing. One measured consequence rules the whole screen: a white key on that ground is only 1.22:1, so elevation alone cannot carry its edge, and every key takes a --c-control-line border — 4.73 on the ground, against WCAG 1.4.11's 3:1. It also shows the full glyph vocabulary — ◇ NEW, ▲ SENT, ✕ VOIDED, ○ OPEN, ◆ offline — because colour never carries meaning alone.

Why it is built this way

Seven rules this screen is proving

tokens.css §3 · WCAG 1.4.11

A device surface, still — just a light one

The scope survived the reversal because it was never about darkness: it is a deeper ground and a tighter density, so a white key face reads as the raised thing. That costs something measurable — white on this ground is 1.22:1 — so every key carries a --c-control-line border at 4.73. Elevation is decoration; the border is the compliance.

design-system §7

The check never unmounts

Categories and the key grid swap around the guest check. Every vendor manual states the same rule outright: the operator must never navigate away to see what has been rung in. Modals are for reason codes, owner approval and errors only — never ordinary ordering.

WCAG 1.4.1 · 1 in 12 men

Colour never alone

Aloha encodes void-versus-delete by item text colour alone. Here every state carries a glyph and a word as well — ◇ NEW, ▲ SENT, ✕ VOIDED plus a strike-through — so red–green colour vision deficiency and counter glare cost nothing.

spec §5 · tokens.css §3b

Bands, not photographs

The reference sells with dish photos. A photo is an image column in the schema, an image payload in the offline menu snapshot and a cache to invalidate on every version bump. Category bands buy the same wayfinding for nothing — and because colour is never the only carrier, the category name is written on every key and every chip. Flagged, not patched: the six band values exist in light only, and measure 1.85–2.33 on the dark key face against 6.13–7.70 on the white one. Six dark values are a tokens.css change and a decision to ask for.

spec §6

Offline is chrome, not a toast

The unsynced count is the one piece of UI the specification mandates outright, and it sits in the status bar permanently. A completed offline cash sale is a recorded fact, not a request — so the number on screen is work the restaurant owns and has not yet handed over.

invariant 7 · spec §17

Each line keeps its own numbers

Under every item is the unit price and the tax rate stored on that line. Discount applies before tax; the screen displays and never calculates. One rounding rule in one function means the check, the invoice and the trial balance cannot disagree — $1.125 becomes $1.13 exactly once.

invariant 9 · spec §8, §14

Approval is a place, not a colour

Discount above the limit and the void of a sent item are gated by owner PIN, so they sit in their own labelled zone behind a divider — and both sit clear of the 96px Pay key. The approval dialog then captures action, employee, approver and reason code in one audit record.
