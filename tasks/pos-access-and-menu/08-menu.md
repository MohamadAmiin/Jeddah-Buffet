# Phase 7 — Menu

The `Menu` rail item becomes real. This phase creates the menu tables with **integer-minor-unit
`bigint` prices**, a domain module in which every write that changes what the POS would download
bumps a `menu_version` in the same transaction, the owner-facing Menu page that enters a price in
major units and converts it **once, server-side**, the two device-authenticated endpoints spec 5
defines (`GET /api/menu/version` with an ETag and `GET /api/menu` with the full snapshot), the POS
side that replaces its local copy atomically, and the onboarding step that reports the menu as done.
The till in this plan still cannot sell: there are no orders, no payments and no journal entries
anywhere in it, and nothing here computes a total.

**Depends on:** Phase 6 (money — T-33's isomorphic core, T-35's formatter and T-36's currency and
tax-mode settings columns), and Phase 3 (the route guard opened for non-dashboard routes, and T-16's
device resolution helper) for the two snapshot endpoints. Phase 0's T-03 must already have recorded
the answers to open decisions 3 (tax mode, rounding, whether a tax rate is per item) and 4 (currency
and its minor-unit exponent); T-37 and T-39 stop if it did not.

3. **`mode: 'bigint'`, never `mode: 'number'`.** `src/lib/server/db/client.ts` installs no type
   parsers on purpose, so `pg` hands back `int8` as a string and this mode turns it into a JavaScript
   `bigint`; `mode: 'number'` would hand money to the one type invariant 1 forbids. `audit_log.id` in
   `src/lib/server/db/schema/audit.ts` is the precedent. `numeric(12,2)` here would be a bug and
   T-04's guard now fails it: `numeric(12,3)` is for ingredient quantities, which belong to the
   inventory plan and are not in this file.
4. **Make `restaurant_id` load-bearing rather than decorative.** The rule, stated once so nothing is
   missed: **every table that is the TARGET of a composite `(restaurant_id, id)` foreign key needs the
   pair-unique index**, because PostgreSQL refuses the FK without it — `there is no unique constraint
   matching given keys for referenced table "<name>"`, at `pnpm db:migrate` time. Three tables are
   targets here, so all three get one:
   `uniqueIndex('menu_categories_id_restaurant_unique').on(table.id, table.restaurantId)`,
   `uniqueIndex('modifier_groups_id_restaurant_unique').on(table.id, table.restaurantId)` and
   `uniqueIndex('menu_items_id_restaurant_unique').on(table.id, table.restaurantId)` — `menu_items`
   included, because `menu_item_modifier_groups` points a composite FK at it. Then reference the
   parents with composite foreign keys instead of single-column ones:
   `foreignKey({ columns: [table.restaurantId, table.categoryId], foreignColumns: [menuCategories.restaurantId, menuCategories.id], name: 'menu_items_category_fk' }).onDelete('restrict')`
   on `menu_items`, the same shape for `modifiers` → `modifier_groups`, and both of them on
   `menu_item_modifier_groups` (item and group). The database then refuses an item in another
   restaurant's category, which a single-column FK would happily accept.
5. Add the CHECK constraints, named, using `check()` from `drizzle-orm/pg-core`:

     negative; a discount is a separate concept with its own approval rule (spec 14).
   - `menu_items_tax_rate_bp_range` — `` sql`${table.taxRateBp} is null or (${table.taxRateBp} >= 0 and ${table.taxRateBp} <= 10000)` ``.
     The rate is **integer basis points**: `825` is 8.25% and `10000` is 100%. Never a float such as
     `0.0825` — `2415 * 0.0825` is `199.23749999999998`, and that error lands inside the money module
     before any rounding.
   - `modifier_groups_select_range` — `` sql`${table.minSelect} >= 0 and ${table.maxSelect} >= ${table.minSelect}` ``.
   - **No** non-negative check on `modifiers.price_delta_minor`: "No cheese −$0.50" is a legitimate
     negative delta. The UI renders a negative with a leading `−` and `--danger`.
6. **Archive, never delete.** `archived_at timestamptz NULL` on categories, items, groups and

   have to alter a populated table later. A read excludes `archived_at is not null`; nothing in this
   plan ever issues a `DELETE` against these four tables.
7. **Leave the recipe seam, do not implement it.** Add **no** recipe column, no `recipe_id`, no
   `cost_minor` and no ingredient reference. Spec 15's recipes link a menu item to ingredients with
   `numeric(12,3)` base-unit quantities and belong to the inventory plan, which has no tables at all

   a guess that a migration then makes permanent. The seam that IS left is the stable
   `menu_items.id`/`modifiers.id` uuid a later `recipes` table references. Cost never lands here
   either: it is the weighted average of the inventory ledger (invariant 6), never a number typed on
   a menu item.
8. **`menu_version` goes on `restaurant_settings`, as
   `menuVersion: integer('menu_version').notNull().default(1)`.** Decided here, with the reason, so
   nobody re-opens it: `restaurants` holds identity — the name printed on receipts and the
   `created_at` the overview reports as "opened on" — and it changes a handful of times in a
   restaurant's life. A counter that increments on every price edit would make `restaurants.updated_at`
   stop meaning "the restaurant record changed". `restaurant_settings` is already the per-restaurant

1. Follow the conventions this codebase already applies in `src/lib/server/restaurants/index.ts`:
   every function takes `restaurantId: string` **explicitly** (there is no ambient tenant), writers
   take `tx: DbTx` and never open their own transaction, readers take `Executor` (`Db | DbTx`) so they
   work on the plain handle and inside a transaction alike. Import both types from
   `$lib/server/db/client` and `$lib/server/auth/session` exactly as that file does.
2. **Make the version bump structural, not a convention a caller can forget.** Write ONE private
   helper and route every write through it:
   ```ts
   async function withMenuVersionBump<T>(
     tx: DbTx, restaurantId: string, write: (tx: DbTx) => Promise<T>
   ): Promise<T> {
     const result = await write(tx);
     await tx.update(restaurantSettings)
       .set({ menuVersion: sql`${restaurantSettings.menuVersion} + 1` })
       .where(eq(restaurantSettings.restaurantId, restaurantId));
     return result;
   }
   ```
   The increment is done **in SQL**, never read-modify-write in TypeScript: two concurrent writes must
   not both read 7 and both write 8. Do **not** set `updatedAt` here — that column means "the owner
   changed a setting" and pairs with the `settings.updated` audit event. The raw insert/update calls
   are module-private; **only** the wrapped functions are exported, so there is no exported path that
   writes a menu row without bumping.
3. Export the writers, each `(tx: DbTx, restaurantId: string, …, ctx: MenuWriteContext)` where
   `type MenuWriteContext = { actorUserId: string | null; ip: string | null; userAgent: string | null }`:
   `createCategory` / `updateCategory` / `archiveCategory`; `createItem` / `updateItem` /
   `archiveItem` / `setItemAvailability`; `createModifierGroup` / `updateModifierGroup` /
   `archiveModifierGroup`; `createModifier` / `updateModifier` / `archiveModifier`;
   `linkModifierGroup` / `unlinkModifierGroup`. Prices cross this boundary as `bigint`
   (`priceMinor: bigint`, `priceDeltaMinor: bigint`), tax rates as `number | null` in integer basis
   points. Every write is scoped `where restaurant_id = $1 and id = $2` — an id alone is a
   cross-tenant write.
4. Export the reads used by later tasks: `getMenuVersion(database: Executor, restaurantId: string): Promise<number>`
   (T-40 calls it) and `listMenu(database: Executor, restaurantId: string)` returning the categories,
   items, modifier groups, modifiers and links with `archived_at is null`, for the dashboard page
   (T-39). `menu_version` is an `integer`, so a plain JavaScript `number` is correct for it —
   `bigint` is for money only.
5. **A no-op write must not bump.** Every `update*` reads the current row inside the same transaction,
   diffs the submitted fields against it, and returns `{ changed: false }` **before** calling
   `withMenuVersionBump` when the diff is empty — the same early return

6. **A price change is audit-logged, in the same transaction** (spec 3 names price changes
   explicitly). Add to `src/lib/server/audit/events.ts`:
   ```ts
   | { event: 'menu.price_changed'; details: {
       target: 'item' | 'modifier'; targetId: string; name: string;
       oldPriceMinor: string; newPriceMinor: string } }
   ```
   and call `writeAudit(tx, …)` from inside `updateItem` when `priceMinor` changed, before the bump.
   **The `target` discriminator is not decoration.** `audit_log` is append-only — migration
   `0004_audit_log_append_only.sql` blocks `UPDATE` and `DELETE` — so a modifier's id filed under a key
   named `menuItemId` would be wrong permanently, and nothing in the row would separate an item price
   change from a modifier delta change. One event with a discriminated `target` keeps the reader, and
   the `EVENT_TEXT` map in step 7, at exactly one entry.
   **The two amounts are decimal STRINGS of the integer minor value** (`850n.toString()` → `"850"`),
   not formatted money and not numbers: `details` is a `jsonb` column and serialising a JavaScript
   `bigint` throws `TypeError: Do not know how to serialize a BigInt`. `assertNoSecrets` (already
   called by `writeAudit`) rejects any key matching `/pass|pin|token|hash|secret|cookie|authorization/i`
   — none of these keys do. Do the same for `modifiers.price_delta_minor` changes from inside
   `updateModifier`, with `target: 'modifier'` and the modifier's id in `targetId`.
7. Add `'menu.price_changed': 'Menu price changed'` to

8. **This module does no money arithmetic and no rounding.** It accepts `bigint` minor units, stores
